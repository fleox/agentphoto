## Invariants and traps

**Templates**

- `template.json` fields are parsed by `parseTemplateInfo` with silent defaults (category `other`, 1200×630): a typo is not an error, it is a wrong card. Keep `id` = folder name, `width` / `height` = `photo.json` `canvas`, `category` one of the use cases agents filter on (`social`, `ad`, `thumbnail`, `product`, `portrait`, `web`, `print`…), a description whose first sentence works alone (it is the table / gallery caption).
- A template with an unparsable `template.json` is silently skipped by `readTemplatesIndex` (CLI `templates list`, MCP, Studio API). `vite.config.ts` `templatesIndex()` parses it too and would break the Studio build instead.
- What reaches the user's project: every file except `photo.json` (rewritten), `agentphoto.json` (regenerated), `template.json` (read for `slot`) and `preview.jpg` / `preview.png` (filtered in both `readTemplateFiles` and `createProject`). `doc.id` becomes the project name, `doc.title` the title; `--size` / `--background` override the canvas.
- **The slot.** `slot` names the image layer that receives the user's photo (`new --template <id> --image <file>`): its `src` is replaced, its `crop` dropped, and an **image mask is deleted** because a pre-computed cut-out belongs to the sample photo. Template assets no layer references after the swap (the sample's cut-out mask) are not copied into the project. Templates that rely on a cut-out (`avatar-pro`, `product-white`, `youtube-thumbnail`) say "run remove_background on the photo layer" in their description; keep that true. Optional `subjectArea` `{ x, y, width, height, anchor? }` (canvas px): the first `remove_background` on the slot after a photo swap fits the subject there (`fitLayer`), e.g. `product-white` stands the product on its floor shadow; use it only where a subject's mask bounding box is a reliable guide (objects, not portraits whose torso runs off the photo). Without a slot (or a slot that is not an image layer) the photo is added at the bottom, covering the canvas.
- Templates reference sample photos as `library:<id>` (0 KB in the template, resolved from the package); copied assets (masks) live under the template's `assets/`. Don't hotlink anything; fonts must be catalog ids.
- Every instantiated template must pass `check` with **zero errors** (the release smoke test checks `social-quote`; the others only by the manual gate). Today two have an avoidable-looking warning (`product-white`, `story-promo`): read it before adding a third.
- `preview.jpg` is a real export of the instantiated template with its sample photo, at most 900 px on the long side (smaller canvases stay at canvas size), JPEG. The README table (absolute `raw.githubusercontent.com` URLs) and both Studio galleries show it; it is never copied into projects.

**Library**

- `index.json` is hand-maintained except the derived fields: `build-library.mjs` recomputes `kb` (sum of files for fonts) and image `width` / `height`; `--check` fails on a missing file, a non-WOFF2 font, an unreadable JPEG, a duplicate id or a stale field. Sample photos must be JPEGs (the script reads the JPEG SOF header).
- The asset id **is** what documents reference (`library:portrait`, font `inter`): renaming one breaks templates, recipes, skills, docs and `agent/e2e.test.ts`. `grep -rn "<id>" templates plugin/skills docs src agent README.md` before renaming.
- A font needs a catalog `FONTS` entry with the same id (family, weights, style), the `index.json` entry with every file and its `unicodeRange`, a `LICENSES.md` row, and Studio labels for a new `style`. Ship only weights the catalog promises; both latin and latin-ext subsets so accented text renders.
- Licences: fonts OFL-1.1 (Roboto Slab Apache-2.0), photos CC0 only, with `author` and `source` recorded. Nothing that needs attribution, an account, a non-commercial or no-derivatives clause enters the library: users export commercial images with it.
- The library ships in the npm package (`package.json → files`) and is copied into `dist/studio/`: keep photos around 1600 px wide and a few hundred KB each.

**Recipes and docs images**

- A recipe is a full document an agent can apply as is: it must validate without warnings (`check:skills`), reference only `library:` photos or files the recipe's commands create, and have been applied, checked and rendered for real. `check:skills` does not render: re-render recipes yourself after a look change.
- `docs/images/*.jpg` are real renders / exports (before / after side by side where relevant), < 150 KB, regenerated with `agentphoto render` / `export` rather than edited. The README and `docs/retouching.md` use them.

## How to add a template

1. Pick an id (kebab case, use case first: `story-promo`, `og-article`); start from the closest template or a size preset: `node dist/agent/agentphoto.mjs new /tmp/t/<id> --template <closest> --json` (or `--size <preset>`, `agentphoto catalog sizes`).
2. Iterate with `doc patch` / `layer add|update` / `filter add`, then `render --project /tmp/t/<id> --json` and **open the PNG**; `--zoom x,y,w,h` for text edges and masks. Name the photo layer clearly and keep it an image layer (it becomes the `slot`).
3. If the design needs a cut-out: `remove-bg <slot> --project /tmp/t/<id> --json` on the sample photo and keep the mask under `assets/masks/`; say in the description that users run remove_background on their own photo.
4. `check --project /tmp/t/<id> --json`: `ok`, no avoidable warning.
5. Copy `photo.json` and `assets/` into `templates/<id>/`; write `template.json` (`id` = folder, `width` / `height` = canvas, category, tags, slot, one-paragraph description).
6. `preview.jpg`: `export --project /tmp/t/<id> --format jpeg --width 900 --json` (or `--height 900` for portrait canvases, no resize when the canvas is smaller) and copy the file from `dist/`.
7. Gate: `new /tmp/t2/<id> --template <id>` then `check` and `render` the fresh project; also with `--image` of another photo to see the slot swap.
8. README templates table row and the count ("8 templates"), `changelog.json` for the next release → [`repo-presentation`](../repo-presentation/SKILL.md). If a skill lists templates (`agentphoto-design`), update it and `npm run hermes:build`.

## How to add a sample photo or a font

1. Licence first: CC0 photo (record author and source URL) or an OFL font from Fontsource / Google Fonts upstream.
2. Photo: JPEG ~1600 px wide under `library/images/`, an `index.json` entry (`id`, `kind: "image"`, `path`, `license`, `author`, `source`, `title`, `tags`, a `description` saying what it is good for). Font: woff2 files under `library/fonts/<id>/`, the `index.json` entry with every file, the catalog `FONTS` entry (`engine-internals`).
3. `node scripts/build-library.mjs` (fills `kb`, `width`, `height`), then `--check`; a `LICENSES.md` row.
4. Render it in a scratch project (`new /tmp/lib/x --size square`, `layer add --src library:<id>` or a text layer with `--set font=<id>`) and look at it.
5. Update counts and lists: skills that list library photos or fonts, `docs/`, README numbers (`agentphoto assets library --json`, `agentphoto catalog fonts --json`).

## Re-rendering after an engine look change

Filters, looks, text, effects or compositing changes shift every look. For each template: instantiate, render, compare with `preview.jpg`, fix `templates/<id>/photo.json` if it no longer looks right, re-export the preview. Re-apply and re-render every recipe in `recipes.md`, regenerate `docs/images/` and hand the README / `.github/assets` stills to `repo-presentation`.

```bash
for t in $(ls templates); do
  node dist/agent/agentphoto.mjs new /tmp/tpl/$t --template $t --force --json > /dev/null
  node dist/agent/agentphoto.mjs check --project /tmp/tpl/$t --json
  node dist/agent/agentphoto.mjs render --project /tmp/tpl/$t --json      # open renders/preview.png
done
```
